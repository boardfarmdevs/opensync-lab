Inside · local-noc/

local-noc, a local OpenSync cloud

A stand-in for the OpenSync cloud that speaks its protocol, OVSDB JSON-RPC (RFC 7047), over plain TCP, keeps a live copy of every node's database, records every message, orchestrates the mesh, and draws the location. Python standard library only.

:6640

Redirector

Where the node's AWLAN_Node.redirector_addr (RDK SONURL) points. Reads the node's identity and assigns the controller.

:6641

Controller

Monitors every table, answers keepalives, holds the live mirror, sends transacts as the cloud.

:8640

Topology view

The web UI and its API, built from the mirrors. See the viewer.

The protocol, message by message

In OpenSync the cloud is the OVSDB client: the node's ovsdb-server opens the connection (an active remote from Manager.target) and the cloud then reads and writes the node's database over it.

1 · The node dials the redirector

With SON enabled, cm resolves redirector_addr and points its Manager.target at it; ovsdb-server connects to tcp:10.101.0.40:6640.

2 · Who are you?

local-noc reads the node's identity:

{"id": 1, "method": "transact", "params": ["Open_vSwitch",
  {"op": "select", "table": "AWLAN_Node", "where": [],
   "columns": ["id", "serial_number", "model", "firmware_version", "redirector_addr", "manager_addr"]}]}

3 · Go to the controller

…and assigns it the controller. The node's cm sees manager_addr and reconnects there.

{"id": 2, "method": "transact", "params": ["Open_vSwitch",
  {"op": "update", "table": "AWLAN_Node", "where": [], "row": {"manager_addr": "tcp:10.101.0.40:6641"}}]}

4 · Learn the database

On the controller connection: list_dbs, then get_schema (mv3's OpenSync 4.4 has 109 tables, the extenders' 6.6 has 135).

{"id": 3, "method": "list_dbs", "params": []}
{"id": 4, "method": "get_schema", "params": ["Open_vSwitch"]}

5 · Monitor everything

One monitor over every table and column. The reply is the whole database; it seeds the mirror.

{"id": 5, "method": "monitor", "params": ["Open_vSwitch", "local-noc",
  {"AWLAN_Node": {}, "Wifi_VIF_State": {}, "Wifi_Inet_State": {}, "Interface": {}, …}]}

6 · Live updates

From then on the node pushes every change as an update notification, applied to the mirror:

{"id": null, "method": "update", "params": ["local-noc",
  {"Wifi_Associated_Clients": {"69f2…": {"new": {"mac": "02:00:00:00:08:00", "state": "active", …}}}}]}

7 · Keepalive

The node probes an idle connection (inactivity_probe, 30 s); local-noc answers, so the session stays up.

{"id": "echo", "method": "echo", "params": []}      # node
{"id": "echo", "result": [], "error": null}         # local-noc

8 · Acting as the cloud

Configuration is a transact on the node's config tables, exactly what the mesh orchestration and noc-ctl transact send, for example mv3's end of an extender's tunnel:

{"id": 9, "method": "transact", "params": ["Open_vSwitch",
  {"op": "insert", "table": "Wifi_Inet_Config", "row": {"if_name": "pgd1_88", "if_type": "gre",
   "gre_ifname": "wl1.1", "gre_local_inet_addr": "169.254.1.1", "gre_remote_inet_addr": "169.254.1.88",
   "enabled": true, "network": true, "mtu": 1562, "ip_assign_scheme": "none"}}]}

Recordings

Every message in both directions, one JSON line each, in /var/lib/local-noc/sessions/<node>/<utc>-<role>-<peer>.jsonl:

{"t": 1790193722.52, "dir": "tx", "role": "controller", "peer": "10.101.0.20:34652", "msg": {"id": 5, "method": "monitor", …}}

Each node's schema and a snapshot of its mirror sit in /var/lib/local-noc/nodes/<node>/.

noc-ctl

Drives a running local-noc through its control socket; from the host as ./deploy-mvx.sh noc ….

commanddoes
nodessessions: node, role, peer, table count, capture file
tables <node>row count per mirrored table
dump <node> <table>the rows of one table, from the mirror
log <node> [N]the last N captured messages of the node's controller session
transact <node> '<op>'…send an OVSDB transact as the cloud
request <node> <method> ['<params>']any JSON-RPC request

Mesh orchestration

With --mesh-gateway, a reconcile loop does for the location what the cloud does. Every few seconds it compares each node's mirror with the desired state and sends only what is missing, so it picks up after restarts and reconnects.

onensures
the gatewaythe backhaul AP (wl1.1): enabled, SSID and WPA2 PSK matching the extenders' onboarding credentials
the gatewaylive OVS counters: stats-update-interval 5 s (mv3 ships 1 hour)
the gatewayper extender associated to the backhaul AP with a lease: a gretap pgd<b3>_<b4> to it, as a port of brlan0
each extenderits fronthaul: home-ap-24 in br-home with the home SSID and PSK, its Wifi_Inet_Config, the radio's channel

Web API

pathreturns
GET /the topology view
GET /api/topologynodes (router, extenders, clients, internet) and links (wired WAN, Wi-Fi backhaul with both GRE ends and counters, client), counts; from the mirrors
GET /api/node/<id>one node's raw mirror: every table as local-noc holds it

How topology.py derives the picture: roles from Connection_Manager_Uplink (an Ethernet uplink is a gateway, a GRE uplink an extender); an extender's backhaul from which AP lists its STA among its associated clients (mv3 reports its VIF MACs as zero, so the STA's parent BSSID alone cannot name the AP's node); clients from the other associations, addressed from the gateway's DHCP_leased_IP; each tunnel's two ends from Wifi_Inet_State and its counters from the gateway's OVS Interface.statistics. Nodes that lose their session stay, greyed, for 10 minutes.
