Stage 1 · build-mvx.sh

Build the mv3 image

A fresh repo init of the mv3 tree, pinned to a known-good reference build down to every commit, built offline, and checked against the reference package for package.

./build-mvx.sh pin                 # once: capture the pins and the pin store from the reference build
./build-mvx.sh build               # fresh checkout + pinned bitbake -> ~/yocto/mv3-lxd-r25-oe40-<MMDD>
./build-mvx.sh build --resume      # continue (or rebuild) an existing build dir
./build-mvx.sh status

What is pinned, and why it works offline

The reference build (~/yocto/mv3-lxd-r25-oe40-0808) is the definition of "known good". Pinning it means three things:

projects

Every repo project

A revision-locked manifest (pins/…/manifest.xml) with each project at the SHA the reference had checked out.

layers

The LXD layers

meta-lxd, meta-lxd-mv3, meta-python2 at the reference's commits (layers.lock).

recipes

Every SRCREV

Most RDK recipes use AUTOREV; the SRCREVs the reference resolved are taken from its buildhistory and forced (srcrev.inc).

Offline: the checkout reads only local git. The local repo mirror is older than the reference build, so a pin store holds one bare repo per project that borrows the mirror's objects through git alternates and adds only the 11 commits the mirror lacks. At build time every remote URL is redirected into the store with process-scoped git config; nothing is written to ~/.gitconfig and the shared mirror is never modified. bitbake itself needs no redirect: the distro builds the RDK components from the checkout's src/, and the remaining git SRC_URIs are pinned and already in the download cache.

The build, step by step

Each step is idempotent (markers in the build dir), so a failed or interrupted build continues where it stopped.

→ → → → → →

pin (once)

From the reference build: a revision-locked manifest generated from the project HEADs (the old repo tool cannot run repo manifest -r under current Python, so lib/pin-manifest.py writes it), the layer commits, every SRCREV (buildhistory-collect-srcrevs -a), the installed package list, and the pin store. The pinned manifest is committed into the store's manifests.git on branch mvx/<pins>.

checkout

repo init of the store's manifest branch with --reference to the mirror, repo sync, then every project's HEAD is compared with its pin. A mismatch stops the build.

layers

The layers that live outside the manifest are cloned from the store and checked out at their pinned commits; their origin is pointed back at the real upstream.

configure

The product's setup-environment creates the build dir; local.conf gets require conf/mvx-srcrev.inc and the shared download and sstate directories.

meta-mvx

This repo's layer of fixes on top of the pinned layers, as bbappends and patches. It is added to bblayers.conf on every build (replacing a meta-mvx of another checkout) and its content hash invalidates the build when it changes. Today it carries two patches to hal-wifi-hwsim, the Wi-Fi HAL that drives the hwsim radios:

  • 0001: report the VAP security and the real BSS state, and keep a running BSS running. Without it mv3's wm re-applied the backhaul VAP every 30 s and each re-apply restarted every BSS, silently dropping the extenders.
  • 0002: forget a station on deauth, disassoc or a new authentication, so an extender that drops and returns can complete the WPA2 handshake again.

The pinned SRCREVs are unchanged; the patches apply on top.

bitbake

bitbake ofw, up to three rounds. A shared sstate object can carry an absolute path into another (possibly deleted) build dir (libwebsockets does); such recipes are detected in the output and rebuilt locally before the next round. With a warm sstate cache a from-scratch build takes about 5 minutes.

verify

The installed package list is compared with the reference's, and every SRCREV both builds recorded with the pins. The last run: 210 packages identical 99 SRCREVs match. The artifact is …/build-exm-qemux86-mv3/tmp/deploy/images/exm-qemux86-mv3/ofw-exm-qemux86-mv3.tar.bz2, and the build dir is remembered in config/local.conf for the next stages.
