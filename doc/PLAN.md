# opensync-lab: implementation plan

Date: 2026-09-22 · Host: rev140 · First target: **mv3, r25-oe40, LXD (exm-qemux86-mv3)**

## 0. Goal and scope

Three entry-point scripts, one per stage, backed by this document:
`build-mvx.sh` (container image), `setup-vm.sh` (lab VM) and `deploy-mvx.sh`
(everything that runs in the VM):

1. **Reproducible build.** It checks out the mv3 LXD build from a *new* `repo init`.
   The checkout is pinned to the same manifest, `meta-lxd*` layer commits, and
   AUTOREV source revisions as the known-good reference build
   `~/yocto/mv3-lxd-r25-oe40-0808`. It uses the mirror
   `~/yocto/repo_reference/mv3-r25-oe40-repo_reference`, then runs bitbake.
2. **Lab VM.** It creates an LXD VM named `opensync-lab-MMDD`. Inside it,
   boardfarm-lab provides the WAN side (DHCP + NAT) and a mac80211_hwsim pool
   provides Wi-Fi radios. `meta-lxd/gen/mv.sh` launches the mv3 container with
   WAN and radios attached.
3. **OpenSync bring-up.** SON is enabled, OpenSync connects to its cloud over
   the WAN, and the node brings up the backhaul VAPs and GRE network that
   external OpenSync nodes attach to.

Out of scope for v1: the other products (mv2plus, mv27, mv37), which get a
config-only extension path (§9). Also out of scope: wmediumd, VM export and
packaging, observability, and changes to the upstream repos beyond small,
separately committed additions such as a boardfarm lab config.

- `repo manifest -r` **fails** in that tree: its bundled `.repo/repo` is old and
  imports the `formatter` module, which Python 3.10 removed. The revision-locked

### 1.2 Build tooling (`~/git/redkite/notes/rdk-b/bash`, `~/yocto/mv-builds`)

- `do-lxd.sh <dir>` derives product, release, and oe from the directory name,
  sources `git-offline.sh`, then runs `repo init --reference …` and `repo sync`.
  It clones meta-lxd, meta-lxd-mvX, and meta-python2, sources `setup-environment`,
  and runs `bitbake ofw`. It **cannot pin** anything, and it **prompts
  interactively** if the directory exists. We reuse its logic and
  `git-offline.sh`, but not the script itself.
- `git-offline.sh`: **bitbucket.upc.biz is currently unreachable from rev140.**
  `offline_git_setup` installs `url.*.insteadOf` redirects that point:
  manifest projects at the repo_reference mirror; `~rvogelaar/meta-lxd*`,
  `rbus-filter`, and `rbus-proxy` at the `~/git/<repo>` working clones; and other
  AUTOREV bitbucket repos (e.g. `hal-wifi-hwsim`,
  `opensync-service-provider-local`) at `~/oe/downloads/git2` caches. It is torn
  down by an EXIT trap.
- Shared caches: `~/oe/downloads` and `~/oe/sstate-cache`. A rebuild with
  identical pins should be mostly sstate hits.

### 1.3 Container launcher `meta-lxd/gen/mv.sh` (+ `gen-util.sh`)

- It must run with `$PWD` under the meta-lxd checkout (`cd meta-lxd/gen`). It uses
  `lxc` and `sudo`. Its `main()` creates the meta-lxd bridges (`wan`, `cm`,
  `wanoe`, `lan-p1..4`, `br-wlan0/1`, `lxdbr1`) and the hwsim pool.
- It detects product and release **from the image path** (`mv3` plus `r25` must
  appear in it). It takes the MMDD datestamp from the 14-digit build stamp in the
  `readlink -f` target.
- The container name is **stable**: `mv3`, or `mv3-0NN` with `-i N`. The serial
  number, MACs, VLAN, nvram volume, and therefore the **OpenSync/cloud node
  identity** all derive from that name.
- mv3 layout: `eth0` is WAN (`-b <bridge>`), `eth1..4` are LAN (`-l <bridge>`
  replaces lan-p1, untagged), `wl0/wl1` are veths on `br-wlan0/1`, and
  **`wlan0..2` are hwsim radios** (`HWSIM_RADIOS`, default 3) moved in as LXD
  `nictype=physical`. They return to the pool on container delete.
- The nvram volume (`mv3-nvram`, pool `default`, mounted at `/data/rdkb_nvram`)
  survives relaunches, so SON settings persist across them.
- The hwsim pool is loaded **once** (`HWSIM_POOL_SIZE=24`, `channels=2`) and never
  reloaded. A free radio is a `virt-wlanN` resident in the host netns with no
  other vifs.

### 1.4 Wi-Fi HAL and OpenSync

- All four `meta-lxd-mvX` machine confs set
  `PREFERRED_PROVIDER_hal-wifi = "hal-wifi-hwsim"`.
- `hal-wifi-hwsim` (at `9f5a5c4` in 0808) provides nl80211 open, WPA2, and
  WPA3-SAE VAPs with an in-HAL authenticator. Its multi-BSS support ("one AP
  netdev per VAP so home + backhaul beacon together") is what lets the cloud's
  `bhaul-ap-*` VAPs come up next to the home VAPs. It reports real VAP state to
  OpenSync.
- `meta-lxd-mv3` lxdinit creates the Broadcom Wi-Fi readiness markers that
  `opensync.init` waits for on mv3.
- Enabling OpenSync (`docs/opensync.md`, boardfarm `tests/opensync`):
  `dmcli eRT setv Device.X_LGI-COM_SON.{SONURL=ssl:wildfire.plume.tech:443,
  NativeAtmBsControl=true, SONOperationalStatus=true, SONLogpullEnable=true,
  SONAdminStatus=true (last)}`. MeshAgent maps SONURL to
  `AWLAN_Node.redirector_addr`, and `cm` connects, which shows as
  `Manager.is_connected=true`.
- **Known limits** (`hal-wifi-hwsim/SETUP.md`, `meta-lxd/docs/opensync-mesh-hwsim.md` §8):
  - Cloud *connect* works (Plume dev/theta).
  - The cloud *pushes config* only after the node is **claimed into a location**
    (serial mapped to a location in the Plume backend).
  - mvx on qemux86 is **gateway-only**: there is no `bhaul-sta` target
    `vif.c`, so an mvx cannot be a cloud-driven *pod*. External OpenSync pods
    must be something else, or the leaf side must be injected
    (`gen/sim-mesh.sh`).
  - Enabling SON in the hardware-less container **breaks LAN DHCP and LAN→WAN
    forwarding until a relaunch** (boardfarm makes these tests opt-in for this
    reason). That is acceptable here, because this lab is dedicated to OpenSync.
  - The hwsim medium without wmediumd can **wedge under churn**. The only cure
    is a module reload, which destroys every container's radios.

### 1.5 boardfarm-lab-staging (GitHub, reachable)

- `main` = `eeb4803`. `bf-lab` reads `lab/$BF_LAB_CONFIG`; relative
  `resources_dir` and `base` paths resolve against `lab/`, so a new lab config
  must live **inside** `lab/`.
- `lab/ca-desk6.json` shows the minimal single-CPE form:
  `"components": {dhcp, wan, lan:false, lan2:false, services:false}`.
- **mv3 WAN is 802.1Q-tagged.** `ca-desk4.json` gives mv3

  gateway `10.70.0.20` (wan-cpe1), and the mgmt subnet is `10.50.0.0/24`.
- CPE slot *N* uses bridges `br-wan10N` and `br-lan20N`. `bf-lab setup` also
  ensures the hwsim pool and sets `bridge-nf-call-iptables=0` after Docker is up.
- `tests/opensync/test_opensync_{managers,cloud}.py` are opt-in via
  `BFT_OPENSYNC_TESTS=1` and are our ready-made acceptance tests.

## 3. Phase 1: pins (`build-mvx.sh pin`)

Capture everything that defines the reference build, once, into
`pins/<product>-<release>-<MMDD>/`. The files are committed to this repo, so
the build is reproducible without the reference tree.

**Pin store (finding while implementing).** The repo_reference mirror is
*older* than the 0808 build: 11 of the 67 pinned commits are not in it. The
reference build had fetched them over the VPN. `pin` therefore creates
`~/yocto/repo_reference/mvx-pins/<pins>/`. It holds one bare repo per project
and layer; each borrows the mirror's objects through git alternates, adds only
the missing commits (190 MB, almost all in `binaries`), and has its branch set
to the pinned commit. The pinned manifest is committed to the store's
`manifests.git` on branch `mvx/<pins>`. The build redirects every remote into
the store using process-scoped git config (`GIT_CONFIG_COUNT`), so neither
`~/.gitconfig` nor the shared mirror is modified. After `pin`, the build no
longer needs the reference tree.

### 3.1 `manifest.xml` (revision-locked)

`repo manifest -r` is unusable (§1.1), so the manifest is built by a small
Python script (stdlib `xml.etree`):

- read `.repo/manifests/<manifest>.xml` (the resolved file behind
  `.repo/manifest.xml`), including any `<include>`;
- for each `<project path=…>`, set `revision="<git -C <path> rev-parse HEAD>"`
  and keep `upstream="<original revision or remote default>"`, so that
  `--current-branch` fetches still know the branch;
- keep `<remote>`, `<default>`, `<linkfile>`, and `<copyfile>` unchanged;
- refuse to write if any project is dirty or has unpushed local commits (all 67
  are clean today).

### 3.2 `layers.lock`

One line per layer that is cloned outside repo:
`meta-lxd rnl25-oe40 15058aa… ssh://git@bitbucket.upc.biz:7999/~rvogelaar/meta-lxd.git`,
and likewise for `meta-lxd-mv3` and `meta-python2`. Values come from
`git -C <ref>/<layer> rev-parse HEAD` and the branch.

### 3.3 `srcrev.inc`

Generated from `<ref>/build-*/buildhistory`. oe-core ships
`scripts/buildhistory-collect-srcrevs`, which emits exactly
`SRCREV:pn-<recipe> = "<sha>"` and handles multi-SRCREV recipes (opensync:
`SRCREV_core/platform/service-provider/vendor`). We use it (with `-a` to include
non-AUTOREV recipes as well) and post-filter only `-native`/`nativesdk`
duplicates. `SRCREV:pn-x` overrides the recipes' weak `SRCREV ?= ${AUTOREV}`.

### 3.4 `reference.txt`

Records the reference build path, manifest name, image file name, build stamp,
and `sha256` of the image. It also records the sha256 of
`buildhistory/images/exm-qemux86-mv3/glibc/ofw/installed-package-names.txt`,
which Phase 2 uses as a reproducibility check.

**Default pins** are `pins/mv3-r25-oe40-0808`. The option `--track-heads`
(Phase 2) deliberately ignores `layers.lock`/`srcrev.inc` for a "latest" build.

## 4. Phase 2: fresh pinned build (`build-mvx.sh build`)

Output directory: `~/yocto/mv3-lxd-r25-oe40-<MMDD>`. The name must keep the
`<product>-lxd-<release>-<oe>-<MMDD>` convention, which `mv.sh` and the
mv-builds tooling parse. The build runs on the **host**, not in the VM, because
it needs the host mirror, `~/git` layers, and `~/oe` caches.

1. **Preflight.** Check for `repo`, `git`, `python3`, and the host tools the build
   expects (`tclsh`, `uuid`, …). Check that the mirror exists and that the target
   directory is absent (refuse unless `--resume`, and **never prompt**). Check at
   least 100 GB free.
2. **Offline redirect.** `source ~/git/redkite/notes/rdk-b/bash/git-offline.sh`,
   then `offline_git_setup "$REPO_REF" "$REPO_REF/.repo/manifests/mv3-r25-oe40.xml"`.
   This is a no-op when bitbucket is reachable, and the EXIT trap tears it down.
   The redirect stays active for all of bitbake, because AUTOREV parsing and the
   fetches need it.
3. **Checkout.**
   `repo init --no-repo-verify --reference="$REPO_REF" -u ssh://git@bitbucket.upc.biz:7999/rdkb/manifests.git -m mv3-r25-oe40.xml`
   (redirected to the mirror), then copy `pins/…/manifest.xml` to
   `.repo/manifests/mvx-pinned.xml` and run
   `repo sync -j8 --current-branch --no-tags -m .repo/manifests/mvx-pinned.xml`.
   Verify every project `HEAD` equals its pinned SHA.
   *Risk:* if a pinned SHA is no longer in the mirror (force-push or gc), fail
   loudly and name the project.
4. **Layers.** For each `layers.lock` entry, run `git clone -b <branch> <url>`,
   which is redirected offline to `~/git/<repo>`, then `git checkout --detach <sha>`
   and verify it.
5. **Environment.** `MACHINE=exm-qemux86-mv3 source meta-lxd-mv3/setup-environment`
   generates `conf/local.conf` and `bblayers.conf` exactly as do-lxd.sh does.
   Copy `srcrev.inc` to `conf/mvx-srcrev.inc` and append
   `require conf/mvx-srcrev.inc` plus `INHERIT += "buildhistory"` (already
   default) to `local.conf`.
6. **Build.** `bitbake ofw`, then `bitbake-layers show-layers > layers.txt`. Log
   to `logs/build-<MMDD>.log`. Success requires bitbake exit 0 **and** the
   artifact existing, following the mv-builds rule that the exit code alone is
   not trusted.
7. **Reproducibility check.** Compare the new `installed-package-names.txt` and
   the pinned `latest_srcrev` set against `reference.txt`. Report differences but
   do not fail. The rootfs tarball itself is not bit-identical (timestamps), so
   compare package lists and versions, not the image hash.
8. **Record** `build-info.json` in the build directory: pins used, host,
   start/end time, image path, sha256, and build stamp.

Idempotency: markers `.mvx-checkout`, `.mvx-layers`, and `.mvx-built` in the
build directory. A re-run resumes at the first missing marker.

## 5. Phase 3: lab VM (`setup-vm.sh`) and deployment (`deploy-mvx.sh`)

Host-side. Default name `opensync-lab-$(date +%m%d)`; the date is fixed once
and stored in `config/local.conf` so later subcommands target the
same VM.

1. **Create.** `lxc init ubuntu:24.04 $VM --vm -c limits.cpu=4 -c limits.memory=8GiB`
   (overridable: `MVX_VM_CPUS`, `MVX_VM_MEMORY`), with the root disk set to 64 GiB
   and the storage pool `MVX_VM_STORAGE` (default: host `default`, ZFS).
   Also set `boot.autostart=false` and `boot.mode=uefi-nosecureboot` (not needed
   for the stock hwsim module, but it keeps the patched-hwsim/wmediumd option
   open). `eth0` is on host `lxdbr0` (NAT gives internet access). Proxy devices
   are optional and off by default.
2. **Wait** for the VM agent (`lxc exec $VM -- true`, 240 s).
3. **Assets**, staged on the host into a temp dir with `SHA256SUMS`, then
   `lxc file push`ed to `/home/mvx/assets/` (the VM cannot reach bitbucket, and
   it has no GitHub SSH key):
   - `meta-lxd.bundle`: a git bundle of the runtime meta-lxd commit. The default
     is the build pin `15058aa`; `MVX_RUNTIME_META_LXD=HEAD` uses `e3d4f23`
     for the wmediumd tooling. It is created from `~/git/meta-lxd` with the same
     `make_bundle` approach as the bpi `build.sh`;
   - `boardfarm-lab-staging.bundle`: pinned commit `MVX_BOARDFARM_COMMIT`
     (default `eeb4803`), cloned or bundled on the host from GitHub;
   - the image `ofw-exm-qemux86-mv3-<stamp>.rootfs.tar.bz2` from the Phase 2 build
     (or from `--image <path>`, e.g. the 0808 reference);
   - `guest/*`, `boardfarm/*`, and `config/mvx.conf`.
4. **Provision**, running guest scripts in order through
   `lxc exec $VM -- env … bash /home/mvx/provision/NN-*.sh`, with
   `exec </dev/null` in each (LXD's stdin YAML-parsing gotcha).

### 5.1 `guest/00-base.sh`

- apt: `docker.io docker-compose-v2 bridge-utils iproute2 iptables iw jq git
  tcpdump iperf3 curl rsync zstd python3 btrfs-progs`, plus
  `linux-modules-extra-$(uname -r)` if `modinfo mac80211_hwsim` fails (the cloud
  image may ship the "virtual" kernel flavour).
- snap `lxd` (channel `MVX_NESTED_LXD_CHANNEL`, default `latest/stable`, matching
  host 6.9), then `snap refresh --hold=forever lxd`. snap `astral-uv --classic`.
- User `mvx` with passwordless sudo, in the `lxd` and `docker` groups.
- `lxd init --auto --storage-backend btrfs` (loop-backed). `mv.sh` hardcodes the
  pool `default` and sets `size=` quotas on the root disk and the nvram volume,
  which btrfs supports.
- Install `mvx-lxd-docker-forward` and its unit: DOCKER-USER ACCEPT for `lxdbr0`
  in and out, copied from `easymesh-lxd-docker-forward`.

### 5.2 `guest/10-hwsim.sh`

- `/etc/modprobe.d/mvx-hwsim.conf`: `options mac80211_hwsim radios=24 channels=2`,
  matching the `gen-util.sh` defaults so that `mv.sh`'s "never reload" check is
  quiet. Also `/etc/modules-load.d/mvx-hwsim.conf`.
- `mvx-hwsim-pool.service` (before `snap.lxd.daemon`): at boot, rename `wlanN`
  to `virt-wlanN` and delete stale vifs. This is a trimmed
  `easymesh-hwsim-pool` without the cfg80211 `lab-netns-owner` check. It is
  needed because LXD profiles reference `virt-wlanN` parents on container start
  after a VM reboot.
- Verify: 24 phys and 24 `virt-wlan*` netdevs in the host netns.

### 5.3 `guest/20-boardfarm.sh`

- Clone `boardfarm-lab-staging.bundle` to
  `/home/mvx/boardfarm/boardfarm-lab-staging`, check out the pinned commit, and
  verify.
- `uv venv` and `uv pip install -e .` into `/home/mvx/boardfarm/.venv`
  (`requires-python >= 3.9`; we use uv's managed Python and record the version).
- **Overlay** `boardfarm/lab/opensync-lab.json` into `lab/`. Boardfarm is used
  only for `bf-lab` (the containers of one vCPE); its testsuite is not run, so
  no inventory is needed. The lab config
  is based on ca-desk6 and ca-desk4:
  ```json
  { "base": "base.json", "lab_name": "opensync-lab",
    "physical_network": {"host_interface": ""},
    "switch": {"mgmt_ip": "", "username": "", "password": ""},
    "components": {"dhcp": true, "wan": true, "lan": true, "lan2": false, "services": false},
    "deployment": {"num_cpes": 1,
      "cpes": [{"name": "mv3", "wan_dot1q_tag": 1081, "mgmt_dot1q_tag": 881}]}}
  ```
  `lan: true` gives `lan-cpe1` on `br-lan201`, a LAN client used to prove the
  datapath *before* SON is enabled.
- `/etc/default/boardfarm-lab` sets `BF_LAB_CONFIG=opensync-lab.json`.
- `bf-lab teardown,setup,status`, retried up to 3 times. The first run builds
  the `bf-dhcp-kea`, `bf-wan`, and `bf-lan` Docker images from Debian bookworm,
  which needs internet access and several minutes.
- Install `boardfarm-lab-rebuild` and `boardfarm-lab.service`, adapted from the
  bpi versions: the container names are `dhcp-cpe1`, `wan-cpe1`, `lan-cpe1`, and
  the readiness gate is Kea running with `eth1.1081` at `10.70.0.10/24`. Set
  `docker update --restart unless-stopped`.
- Gate (**L0**): `br-wan101` and `br-lan201` exist, the three containers are
  running, Kea v4 and v6 are up, and `wan-cpe1` can `ping 8.8.8.8`.

### 5.4 `guest/30-mvx.sh` + `guest/40-wan-check.sh` (`deploy-mvx.sh push|launch|check`)

- Clone `meta-lxd.bundle` to `/home/mvx/git/meta-lxd` at the runtime commit.
- Stage the image so that `mv.sh` can parse it:
  `/home/mvx/images/mv3-lxd-r25-oe40-<MMDD>/ofw-exm-qemux86-mv3-<stamp>.rootfs.tar.bz2`,
  plus a symlink `ofw-exm-qemux86-mv3.tar.bz2` to it. The path supplies `mv3`
  and `r25`, and the symlink target supplies the 14-digit stamp.
- Launch:
  ```sh
  cd /home/mvx/git/meta-lxd/gen
  HWSIM_RADIOS=3 ./mv.sh /home/mvx/images/mv3-lxd-r25-oe40-<MMDD>/ofw-exm-qemux86-mv3.tar.bz2 \
      -b br-wan101 -l br-lan201 ${MVX_INSTANCE:+-i $MVX_INSTANCE}
  ```
  This yields a container `mv3` (or `mv3-0NN`) with `eth0` on `br-wan101`,
  `eth1` on `br-lan201`, and `wlan0..2` from the pool.
- Gate (**L1**): within 300 s, `erouter0` has an IPv4 in `10.70.0.0/24`, the
  default route goes via `10.70.0.20`, `ping -c3 8.8.8.8` succeeds from the
  container, and `nslookup wildfire.plume.tech` resolves. `lan-cpe1` gets a
  DHCP lease from mv3 and reaches `8.8.8.8` (pre-SON datapath proof).
- Gate (**L2**): `wlan0..2` are present in the container,
  `grep -a -c sim_hw_nl_enum /usr/lib/libhal_wifi.so*` is greater than 0, and
  CcspWifi has brought up the home VAPs (`iw dev` shows type AP interfaces).
- Record `lxc config get mv3 user.build` and the launched image in
  `/var/lib/opensync-lab/deploy.json`.

### 5.5 `guest/50-opensync.sh` (planned: `deploy-mvx.sh opensync`)

- Preconditions: router mode (`syscfg get bridge_mode` is `0` or empty), and
  `/usr/opensync/scripts/opensync.init` is present.
- Enable SON through dmcli, in the order used by boardfarm's
  `test_opensync_cloud`: SONURL (`MVX_OPENSYNC_REDIRECTOR`, default
  `ssl:wildfire.plume.tech:443`), NativeAtmBsControl, SONOperationalStatus,
  SONLogpullEnable, and SONAdminStatus last. Do not reboot unless the managers
  fail to start; then run one `lxc restart` as a fallback. SON state persists in
  nvram.
- Gate (**L3**): `dm`, `cm`, `nm`, `owm`, and `ovsdb-server` are running within 180 s.
- Gate (**L4**): `AWLAN_Node.redirector_addr` contains the redirector host within
  60 s, and `Manager.is_connected == true` within 180 s. If
  `AWLAN_Node.manager_addr` stays empty, report **"connected to redirector, no
  controller assigned: node not claimed"** and do not treat it as a failure.
- Observation (**L5**, cloud-driven, needs a claimed node): `Wifi_VIF_Config` and
  `Wifi_VIF_State` contain `bhaul-ap-*` rows, and the backhaul SSIDs beacon on
  the hwsim medium. The beacons are checked by a scan from a borrowed pool radio
  in a throw-away netns or `wlan-client.sh`, not from the mv3 radios.
- Observation (**L6**): when an OpenSync pod associates to `bhaul-ap-*`, a
  `g-<mac>` gretap appears in `Wifi_Inet_State` (if_type `gre`) and is a port of
  the home bridge. With no pod present, L6 is reported as "waiting for extender".
- Dump the OVSDB tables `AWLAN_Node`, `Manager`, `Wifi_Radio_State`,
  `Wifi_VIF_State`, and `Wifi_Inet_State` to `/var/lib/opensync-lab/ovsdb-<ts>.txt`.

### 5.6 `guest/60-mesh.sh` (optional, planned: `deploy-mvx.sh mesh`)

This proves the GRE side without waiting for claiming. It follows
`opensync-mesh-hwsim.md`:

- Launch a leaf with `mv.sh <img> -i 2` (no WAN, 3 radios).
- `GW=mv3 LEAF=mv3-002 ./sim-mesh.sh all`: backhaul on `wlan2`, `nm`-built
  `gre-bhaul` gretap on both ends, the leaf's `br-mesh` plus client AP, and a
  netns Wi-Fi client that gets DHCP from mv3 over the tunnel and pings `8.8.8.8`.
- This is **injected orchestration**, not cloud-driven. It is kept separate so
  that the L4/L5 cloud results stay clean. It is mutually exclusive with a
  claimed-cloud run on the same gateway, because the cloud would overwrite the
  injected `Wifi_Inet_Config`.

### 5.7 `guest/90-check.sh` (planned: `deploy-mvx.sh report`)

This prints and writes `status.json` for tiers L0 through L6, with PASS, FAIL,
WAIT, or SKIP and a one-line reason each. The host subcommand runs it through
`lxc exec`. The boardfarm testsuite is out of scope: boardfarm provides the
lab containers (`bf-lab`) only.

### 5.8 Reboot behaviour

`mvx-lab.service` runs after `boardfarm-lab.service`,
`mvx-lxd-docker-forward.service`, and `mvx-hwsim-pool.service`. It starts `mv3`
(created with `boot.autostart=false`) only after the WAN gate passes. The VM
itself is `boot.autostart=false`, so it never starts just because rev140
rebooted.

### 5.9 OpenSync extender (pod) and local-noc mesh (`build-pod.sh`, `deploy-mvx.sh pod|client|mesh`)

The extender is built from the open-source OpenSync release, not from the
RDK tree, and runs as an LXD system container in the same VM (the hwsim
medium is per kernel):

- **Build** (`build-pod.sh`, host): OpenSync **6.6.1.0** from
  github.com/plume-design, pinned in `pod/opensync/sources.lock`: core,
  `opensync-platform-cfg80211` (nl80211, i.e. mac80211_hwsim),
  `opensync-vendor-openwrt-template` with our `HWSIM_POD` target overlaid
  (`pod/opensync/vendor-overlay`), and our `mvx-local` service provider
  (redirector `tcp:10.101.0.40:6640`, onboarding backhaul credentials).
  Compiled natively in an Ubuntu 20.04 docker build environment (OVS 2.8.7,
  hostap `d9d5e55` with OpenSync's patches), not with the OpenWrt SDK. Our
  patches to upstream live in `pod/opensync/patches/<repo>/`. Output: an LXD
  image (`mvx-pod-<stamp>.{metadata,rootfs}.tar.gz`, Ubuntu 20.04 + systemd).
- **Pod** (`guest/70-pod.sh`): two hwsim radios as `wlan0/1` and **no wired
  NIC**. A runtime bootstrap (`mvx-pod-bootstrap`) binds OpenSync's radio
  config to the phys actually present (wiphy names are VM-wide and cannot be
  renamed): 1st radio 2.4G (fronthaul), 2nd 5G with the `bhaul-sta-50` VIF.
  `cm` then onboards exactly as on hardware: the STA joins the gateway's
  backhaul AP, DHCPs a 169.254 address, builds `g-bhaul-sta-50` to the
  gateway, bridges it into `br-home`, gets a LAN lease through it, and
  reaches the redirector/controller.
- **local-noc mesh** (`local-noc/mesh.py`, `--mesh-gateway`): does for the
  location what the cloud does -- enables the gateway's backhaul AP
  (`wl1.1`, WPA2 with the pod's onboarding credentials), creates the
  gateway's end of each pod's tunnel (`Wifi_Inet_Config` `pgd<b3>_<b4>`, if_type
  gre) and adds it to `brlan0` via the OVS tables once the pod is associated
  and leased, and gives each pod that connects its fronthaul (`home-ap-24`
  in `br-home`, home SSID). All over OVSDB, recorded like everything else.
- **Client** (`guest/80-client.sh`): an Alpine container with one hwsim radio
  and no wired NIC; `wpa_supplicant` joins the pod's fronthaul, DHCP comes
  from mv3 across the tunnel, and ICMP/DNS/HTTP reach the internet.

The Plume-cloud variant (pod claimed into the theta location, the cloud
building the GRE) needs the pod's identity registered with that cloud and is
a follow-up; the injected `sim-mesh.sh` path (§5.6, `deploy-mvx.sh gre`) is
kept alongside.

## 6. Success criteria

| Tier | Meaning | Check |
|---|---|---|
| B | Pinned build reproduces the reference | every project/layer SHA equals its pin; artifact exists; package list matches `reference.txt` |
| L0 | VM + boardfarm WAN up | containers running, Kea v4 and v6 on `eth1.1081`, wan-cpe1 has internet |
| L1 | mv3 WAN up | erouter0 in 10.70.0.0/24; ping 8.8.8.8; DNS resolves the redirector; lan-cpe1 has internet via mv3 |
| L2 | Wi-Fi HAL on hwsim | 3 radios in the container; home VAPs are type AP |
| L3 | OpenSync running | dm/cm/nm/owm/ovsdb-server running |
| L4 | Cloud connection | redirector_addr set; `Manager.is_connected=true` |
| L5 | Cloud config (claimed node) | bhaul-ap VAPs configured and beaconing |
| L6 | GRE backhaul | `g-*` gretap in `Wifi_Inet_State` when a pod joins (cloud) **or** `sim-mesh.sh` client internet over the GRE (injected) |
| L7 | OpenSync extender | pod onboards over the Wi-Fi backhaul (both GRE ends, LAN lease), is claimed by local-noc and gets its fronthaul; a wireless client behind it reaches the internet (`deploy-mvx.sh mesh`) |

The v1 "done" bar is **B + L0–L4 automated and green**. L5 and L6 are reported
honestly: they depend on claiming and on an external pod.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A pinned SHA is missing from the mirror | the pin step checks each SHA in the mirror (`git cat-file -e`) at capture time; the build fails with the project name |
| AUTOREV recipe not in buildhistory (e.g. not in the image) | `srcrev.inc` covers all built recipes; the build diffs `bitbake -e` resolved SRCREVs against the pins for image recipes and warns |
| bitbucket returns (VPN up) mid-way | `git-offline.sh` is a no-op online; pins make the result identical either way |
| Old `.repo/repo` or Python mismatch | pass `--repo-rev=stable` to `repo init`; pin generation never calls `repo manifest` |
| Node identity collision: container `mv3` in the VM has the same serial/MAC as `mv3` on rev140 or another VM | `MVX_INSTANCE` (`-i N`) gives a distinct identity; the check warns if the host already runs `mv3` with SON on (**open question Q1**) |
| Docker FORWARD DROP / bridge-nf eats frames | `mvx-lxd-docker-forward`; `bf-lab` sets `bridge-nf-call-iptables=0` after Docker is up; the check verifies it |
| hwsim medium wedges | fresh VM per run is cheap; `setup-vm.sh reset-radios` (planned) (stop containers, reload module, relaunch); wmediumd as a later option |
| Nested LXD quota support | btrfs default pool in the VM; fallback `MVX_NESTED_STORAGE=dir` with the `mv.sh` size keys dropped would need a meta-lxd change, so prefer btrfs |
| SON breaks LAN datapath | expected (§1.4); L1's LAN proof runs before SON; lan-cpe1 results after SON are informational |
| Cloud never pushes config | this is a claiming/backend issue, not a lab bug; L4 vs L5 split makes it visible; `mesh` provides the local GRE proof |

## 8. Script interfaces

```
build-mvx.sh  pin [--from DIR]            capture pins + pin store from a reference build
build-mvx.sh  build [--dir DIR] [--resume] fresh repo init + pinned bitbake + verify
build-mvx.sh  all | status [DIR]

setup-vm.sh   create | provision | all     create + provision the VM (idempotent)
setup-vm.sh   status | shell | start | stop | delete

deploy-mvx.sh push [--image PATH]         image + pinned meta-lxd bundle into the VM
deploy-mvx.sh launch | check | all        mv.sh launch, WAN check
deploy-mvx.sh opensync [--cloud plume|local] | gre
deploy-mvx.sh pod | client | mesh         OpenSync extender, wireless client, both (§5.9)
deploy-mvx.sh noc <noc-ctl args> | status | shell
              (planned: report)

build-pod.sh  buildenv | sources | build | image | all | status
```

Conventions: `set -euo pipefail`. Every step is idempotent: markers in the
build directory, and `/var/lib/opensync-lab/*.status` in the VM. Logs go to
`logs/<cmd>-<ts>.log`. Nothing prompts except `setup-vm.sh delete`. All
settings are in `config/mvx.conf` and can be overridden from the environment.

## 10. Implementation order
